Projects and Implementations in the Client Portal

Taking implementation projects out of a tool of their own and building them into the portal clients already use.

01

Context

A Fiserv client in the middle of an implementation had their project in one place and everything else in another. Project work lived in a standalone tool. Support inquiries, documentation and self-service lived in the client portal. The two never met, even though a client's questions during an implementation are almost always about the implementation.

02

My role

I drove requirements for moving projects and implementations into the portal: who the stakeholders were, what belonged in the MVP, what depended on what, and how the experience should work once it was there.

03

Build it in, don't link out

The cheap option was to link out from the portal to the tool that already existed. It ships faster and it leaves the split exactly where it is: the client still ends up in two applications, learning two sets of conventions, with no relationship between a project and the support raised against it.

We built it natively instead. That is more work up front and it is the reason the rest of this holds together, because once a project lives in the portal it can be connected to the inquiries, documentation and account data already there.

04

What a client can do

  • See the projects they have, and where each one has got to.
  • Upload project documentation.
  • Add notes against the project.
  • Make requests.
  • Raise and track support inquiries, in the same application rather than a different one.

05

The hard part: data people can trust

The tool pulls from a lot of upstream systems, so it is only ever as current as they are. If the people who own a source don't keep it updated, the client sees something stale in a place that looks authoritative, which costs more trust than showing nothing would have.

Two things run alongside the build, and neither is finished:

  • Training for the teams who own the upstream data. Most of the fix is upstream rather than in the interface, so the work is with the people maintaining the sources.
  • Only surfacing data we can stand behind. Where accuracy isn't dependable yet, it doesn't ship. One wrong project status costs more than a missing one, both with clients and with the internal teams who have to answer for it.

06

The same idea as Ask 360

Both halves of the portal work push the same way: give the client one application instead of several, and carry their context across it instead of making them re-establish it. Ask 360 does that inside a single conversation, so nobody retypes the situation they already described. Projects does it across the portal, so the work a client is in the middle of sits next to the help they need with it.
