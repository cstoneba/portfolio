Ask360: AI Support Assistant

Redesigning how financial-institution clients get service, from the interviews that mapped the problem through an AI assistant built into the portal as one continuous journey. Piloting with 400 clients.

Experience design Conversation design User research Requirements

01

Context

Fiserv's client support portal is where financial-institution clients go when something isn't working. Getting to an answer was the problem. Knowledge articles and product documentation were hard to surface through search, and what did surface wasn't always current. When search failed, the client opened an inquiry and retyped the whole situation from scratch.

Ask360 is the redesign of that experience. A client describes the problem in their own words, gets documentation back for the products they actually license, and if that doesn't resolve it, opens an inquiry from inside the same conversation with the context already attached. One journey instead of three.

02

My role

I was the primary designer. I ran the interviews that defined the problem, designed the experience through successive rounds of iteration, and built the working prototype with Figma Make and GitHub Copilot. I also wrote the requirements and acceptance criteria that engineering and the knowledge-platform team built against, including the rules for what the assistant may surface and to whom.

03

Process

Starting with how service actually worked

Before designing anything I interviewed clients about how they got help today: what they searched for, where they gave up, and what they did next. The pattern was consistent enough to design against. Search rarely surfaced the right article, what it did surface wasn't always current, and the fallback was always an inquiry that meant retyping everything. That reframed the problem as the whole service journey rather than a missing chatbot.

Redesigning the experience in iterations

I designed the experience in rounds instead of one handoff: redesign the flow, put it in front of people, change what didn't work, go again. I did the visual design and built each version into a clickable prototype with Figma Make and GitHub Copilot, so every round could be judged as a real experience rather than a static screen. Each pass tightened the path from describing a problem, to reading something that helps, to opening an inquiry only if one is still needed.

Building an assistant that knows the client

We partnered with Sierra to build the assistant itself, giving it the client's details so it could help someone troubleshoot instead of returning the same generic documentation search already returned. That context is the whole difference: it answers against the products a client actually licenses and the state of their account, so the response fits their setup rather than describing features they don't own.

Making it native rather than bolted on

A chat widget dropped into the corner of the page would have left the broken journey intact underneath it. We integrated the assistant into the portal as a native experience with one continuous journey: describe the problem, troubleshoot with what comes back, and open an inquiry from inside the same conversation, context already attached, without duplicating the work by retyping it.

Respecting what each user is allowed to do

Permissions vary between users inside the same client organization. Some can create inquiries, some can view projects or invoices, some can't. The assistant reads those permissions and adapts to them: it won't offer to open an inquiry for someone who has no rights to create one, and it won't reference an invoice that person can't see. Writing that as acceptance criteria meant enumerating the permission combinations and defining what the assistant should say in each.

Designing for whatever screen it opens on

Clients open the portal from a desk and from a phone between meetings, so the assistant is adaptive rather than desktop-only. The same conversation, documentation, and inquiry flow had to hold up at desktop, tablet, and mobile widths, which meant designing how the chat panel, the returned articles, and the inquiry form reflow instead of assuming full-width layout.

Writing it down so it could be built

Alongside the design, I documented 40+ conversational use cases and their edge cases: what happens when the assistant doesn't have enough data to answer, when a client asks something out of scope, and when the documentation can't resolve it and the client needs to open an inquiry instead. Each one got acceptance criteria, so engineering had a clear definition of "done" and QA had something concrete to test against.

Testing, then keeping the loop open

I ran Wizard of Oz sessions with 10 client users, playing the assistant myself behind the prototype so people could work through real problems before any of the model behaviour was built. Where someone got stuck, described a problem in words the flows didn't anticipate, or expected an action the assistant never offered, I changed the flows and the copy between sessions.

That didn't stop once it was built. We host recurring feedback sessions to hear how clients are actually using it, what works and what doesn't, and each round feeds the next: more functionality, and an assistant that feels more native to the portal each time.

04

Collaboration & stakeholders

The design only holds up if several groups agree on the same set of constraints: Sierra needs to know what the assistant should be able to do and with which client data, engineering needs to know what's buildable and where the data boundaries are, the knowledge-platform team needs to know which content gaps to fill so there's something accurate to draw from, and the teams that own account and permissions data need to agree on precisely what can be exposed and to whom. Keeping that consistent, and re-aligning it every time a feedback session surfaced something new, was most of the day-to-day work.
